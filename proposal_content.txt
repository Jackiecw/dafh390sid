
根据您的需求以及您提供的 TikTok 和 Shopee 导出文件，我为您梳理了关于优化“销售数据录入”板块的建议。您的核心目标是从手动汇总录入转变为基于订单的自动化录入，这将极大提高数据的准确性和颗粒度。
以下是针对数据库、数据映射、业务逻辑和功能的具体优化建议：
1. 数据库模型优化建议 (SalesData 表)
目前的 SalesData 表结构主要是为了存储按天汇总的数据。为了支持订单级管理和退货逻辑，建议对 Schema 进行如下调整：
新增 platformOrderId (订单号)：
建议：添加 platformOrderId 字段，并设为唯一索引 (Unique Index)。
目的：这是防止重复录入的关键。每次上传文件时，系统可以通过此字段判断该订单是否已存在。
新增 orderStatus (订单状态)：
建议：添加状态字段（如 COMPLETED (正常), RETURNED (已退货), CANCELLED (已取消)）。
目的：为了后续的“退货”功能。如果订单发生退货，您不需要删除数据，而是将状态改为 RETURNED，并在统计报表中排除这部分金额。
新增 quantity (数量) 和 unitPrice (单价)：
建议：虽然现有表有 salesVolume 和 revenue，但在订单级数据中，明确单价和数量有助于核对数据。
关联调整：
目前的 SalesData 关联了 listingId。在导入时，系统需要根据 Excel 中的 "Seller SKU" 自动查找对应的 listingId。
2. 平台数据提取与映射建议
根据您提供的 Excel 文件，以下是针对字段提取的详细建议：
A. Shopee (参考文件: 虾皮1日.xlsx)
订单筛选 (Filter)：
逻辑：您提到只考虑正常/预购，不含取消/未付款。
字段：Status Pesanan (订单状态)。
建议：
保留：Perlu Dikirim (待发货), Sedang Dikirim (运输中), Selesai (完成)。
排除：Belum Bayar (未付款), Batal (已取消), Pengembalian (退货/退款)。
销售额 (Revenue)：
您提到的字段：Harga Setelah Diskon (折后单价)。
潜在风险：这个字段通常是单件商品的价格。如果一个订单买了 2 个同款商品，直接用这个字段会导致金额少算一半。
优化建议：应使用公式计算或取总额列。
方案一（推荐）：使用 Total Harga Produk (商品总价) 列（文件中是 Total Harga Produk）。这通常已经包含了 单价 x 数量。
方案二：Harga Setelah Diskon (单价) * Jumlah (数量)。
SKU 匹配：
使用 Nomor Referensi SKU (主要) 或 SKU Induk。系统需拿这个值去匹配您 StoreProductListing 表中的 productCode。
B. TikTok Shop (参考文件: TK近7日.xlsx)
订单筛选 (Filter)：
字段：Order Status。
建议：
保留：Awaiting Shipment, Awaiting Collection, In Transit, Delivered, Completed。
排除：Unpaid, Cancelled。
销售额 (Revenue)：
您提到的字段：Order Amount。
潜在风险：Order Amount 通常是买家支付的总金额，包含运费 (Shipping Fee) 和税费。如果您想统计的是纯货款（GMV），这个值可能会偏高。
优化建议：
建议检查 SKU Subtotal After Discount (SKU折后小计)。这一列通常代表扣除折扣后的纯商品收入，不含运费，作为销售业绩更准确。
SKU 匹配：
使用 Seller SKU 字段与系统内的 productCode 进行匹配。
3. 批量录入与交互流程建议
您提到的“上传 -> 提取 -> 弹窗确认 -> 录入”是一个非常标准的最佳实践。建议流程细节如下：
文件解析 (Pre-process)：
后端接收文件，根据文件名或内容特征自动识别是 Shopee 还是 TikTok。
根据上述逻辑过滤掉无效订单（未付款/取消）。
关键步骤：根据 Excel 中的 SKU，尝试在数据库中查找对应的 listingId。
弹窗确认 (Preview & Fix)：
展示内容：返回一个列表给前端，包含：订单号、SKU、匹配到的系统商品、金额、状态。
异常处理：
SKU 未匹配：如果 Excel 中的 SKU 在系统中找不到，该行应标红。允许运营人员在弹窗中手动下拉选择对应的系统商品链接（Listing），或者选择“忽略此条”。
订单已存在：如果订单号已存在数据库，提示“跳过”或“覆盖更新”。
批量提交 (Commit)：
用户确认无误后，点击提交，后端执行批量插入（createMany）。
4. 关于“退货”功能的后续规划建议
您提到后续要处理退货并扣除销售额。为了实现这一点，现在的架构需要做如下准备：
导入逻辑支持“更新”：
运营人员可能会定期导入最新的订单报表。如果一个旧订单（之前是 Completed）在新的报表中变成了 Returned 或 Refunded。
建议：系统应识别 platformOrderId 已存在，并比较状态。如果状态变更为退货/退款，则更新数据库中的状态字段。
销售额统计逻辑：
在 Dashboard 或报表统计 GMV 时，查询条件应变更为：WHERE status != 'RETURNED'。
或者，您可以设计一个逻辑：当状态变为退货时，将 revenue 更新为 0 或负数（取决于您的财务核算方式），这样求和时自动扣除。建议更新状态为 RETURNED 并在统计时过滤掉，这样保留了原始数据，也方便统计“退货率”。
5. 总结
数据表：必须加 platformOrderId (Unique) 和 status。
Shopee 金额：请改用 Total Harga Produk 或 单价 x 数量，不要只用单价。
TikTok 金额：请确认是否包含运费，建议对比 Order Amount 和 SKU Subtotal After Discount。
核心体验：把精力放在“SKU 自动匹配失败的处理”上，这是批量导入中最耗时的地方。

以下是对你这套方案的详细评估和优化建议：
一、 关于“利用商品标题匹配 Listing”的逻辑评估
你的逻辑： 国家 -> 平台 -> 店铺 -> 匹配标题 -> 锁定 listingId。
评价：
这是解决“同产品多链接”归因问题的唯一办法。因为 SKU 是相同的（对应库存），只有标题（Listing Title）能区分流量入口。
潜在风险与优化建议：
标题一致性风险：
问题：平台导出的 Excel 中的标题（如 [大促特惠] 商品A...）可能和你系统中 StoreProductListing 表里存的标题（如 商品A...）不完全一致（多了前缀、后缀，或者因为截断而不完整）。
建议：
精准匹配优先：先尝试 100% 字符完全匹配。
建立“别名映射”机制：如果系统发现 Excel 里的标题是“A”，但数据库里是“B”，在弹窗手动匹配时，增加一个“记住此匹配关系”的选项。下次再遇到“A”，系统自动知道它属于 listingId_B。这会越用越顺手。
匹配失败的处理（你的弹窗逻辑）：
建议：在上传后的确认弹窗中，将匹配失败的行置顶并标红。提供一个下拉框，下拉框里列出该店铺下所有的在售链接（显示：图片 + 标题 + SKU），让运营人员手动“点选”一下即可。
二、 关于“每日新增 + 周一更新状态”的业务逻辑
你的逻辑：
日常：上传昨日数据 -> 主要是为了录入新订单（状态可能是“待发货”）。
周一：上传过去7天数据 -> 主要是为了更新旧订单的状态（变成“已完成”、“已退货”）。
评价：
这是一个非常经典的**Upsert（更新或插入）**策略，既保证了数据的实时性（每天看昨日销量），又保证了数据的最终一致性（状态更新）。
优化建议：
唯一索引是核心：
必须确保数据库中 SalesData 表的 platformOrderId（订单号）是唯一索引。
处理逻辑：后端在处理 Excel 时，如果发现订单号已存在：
不跳过，而是更新该条记录的 status（状态）、updatedAt（更新时间）。
关键点：如果订单状态变成了“退货/取消”，同时需要更新 revenue（销售额）。（有些公司退货算负销售额，有些是记为0，看你财务习惯，建议记为0或者由专门的退款字段记录）。
销售额的变动：
有时订单金额在“待支付”转“已支付”或“发货”时，因为汇率或平台补贴，金额会有微小变化。
建议：在“周一更新”模式下，除了更新状态，建议也覆写一次销售额，以平台最新的结算金额为准。
三、 关于“上传前选择平台”与“防呆验证”
你的逻辑： 用户手动选平台 -> 上传文件 -> 系统校验 -> 弹窗报错。
评价：
这能极大减少后端解析的复杂度，避免系统去猜测文件格式。
优化建议：
表头指纹校验 (Header Check)：
即便用户选了“Shopee”，他可能还是手滑传了“TikTok”的表。
建议：后端配置一套简单的指纹规则。
如果选了 Shopee，系统检查文件第一行必须包含 No. Pesanan 或 Order ID 且包含 Status Pesanan。
如果选了 TikTok，系统检查文件第一行必须包含 Order ID 且包含 Order Status。
如果规则不匹配，直接前端弹窗：“您选择了 Shopee 平台，但上传的文件格式看起来像 TikTok 或未知格式，请检查。”
四、 针对你提到的金额字段确认
根据你提供的文件，我的确认如下：
TikTok Shop (TK近7日.xlsx)：
你选择：Order Amount。
我的观察：Order Amount 通常是买家实付金额（包含运费）。
更优选：建议使用 SKU Subtotal After Discount (SKU折后小计)。
原因：你统计的是“链接销售表现”，应该剥离运费。SKU Subtotal After Discount 是纯货款扣除折扣后的金额，更能反映运营能力。如果用 Order Amount，运费波动会干扰你判断哪个链接卖得好。
Shopee (虾皮1日.xlsx)：
你选择：Harga Setelah Diskon (折后单价)。
我的观察：这只是单价。
必须修正：必须是用 Total Harga Produk (商品总价)。
原因：如果一个订单买了 2 个同款，Harga Setelah Diskon 还是显示 1 个的价格，你会少算一半销售额。Total Harga Produk 才是这一行 SKU 的总销售额。
五、 总结后的推荐流程
用户操作：点击“批量导入” -> 选择“Shopee” -> 拖入 Excel。
前端/后端校验：检查表头是否包含 No. Pesanan。如果不包含，报错。
数据解析：
系统提取 Excel 每一行。
匹配 Listing：拿 Excel 里的 Nama Produk (商品标题) 去数据库 StoreProductListing 表里找一模一样的标题。
找到了 -> 记下 listingId。
没找到 -> 标记为“待确认”。
预览弹窗：
显示：订单号 | 标题 | 匹配状态 (成功/失败) | 金额 | 状态。
对于“匹配失败”的行，用户手动在下拉框选一下是哪个链接。
确认提交：
后端执行 upsert：
订单号不存在 -> 新增一条销售记录。
订单号已存在 -> 更新该记录的状态 (Status) 和金额 (Revenue)。
如果新状态是“退货/取消” -> 根据规则扣除业绩。
这个方案逻辑闭环，既解决了多链接归因，又解决了数据维护问题。可行！
